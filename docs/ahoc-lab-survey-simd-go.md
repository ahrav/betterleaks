# Go-on-arm64 SIMD implementation space for the betterleaks prefilter — research findings

## (1) GOEXPERIMENT=simd status (Go 1.25/1.26/1.27)

**Proposal**: golang/go **#73787** (`simd/archsimd`, filed by cherrymui 2025-05-19, **Accepted**). Two-level design: arch-specific intrinsics now ("analogous to `syscall`"), portable high-level API later. Renamed `simd` → `simd/archsimd` per **#76473**.

**Shipping state (verified against release notes + issue timeline)**:
- **Go 1.25**: nothing; dev happened on `dev.simd` branch (amd64 preliminary impl announced 2025-08-20).
- **Go 1.26** (released 2026-02-11): `simd/archsimd` under `GOEXPERIMENT=simd`, **amd64 ONLY** (AVX-form, 128/256/512-bit types `Int8x16`…`Float64x8`). Release notes: "currently available on the amd64 architecture… We intend to provide support for other architectures in future versions." API explicitly unstable.
- **Go 1.27 RC1** (2026-06-23): "revises the amd64 API and **adds support for arm64 'Neon' 128-bit SIMD** and WebAssembly 128-bit SIMD" — 128-bit vector types only on arm64. Also adds experimental **portable `simd` package** (#78902, size-agnostic types like `Int8s`), "scalable subset" of ops. SVE explicitly deferred to future work. Breaking API changes vs 1.26.
- **pkg.go.dev simd/archsimd@master** (fetched 2026-07): arm64 present via the shared type set (not a separate NEON API); `ARM64Features.PMULL()` for feature detection. Ops relevant to a 16B classification loop **exist at master**: `Int8x16.PermuteOrZero(indices)` (= NEON **TBL**, out-of-range→0), `ConcatPermute` (TBL2), `Equal` (CMEQ), `And/Or/Xor/AndNot`, `ToBits()` (movemask synthesized — expensive on NEON), `IsZero()` (cheap any-hit test), `Compress/Expand`, `LoadInt8x16`/`Store` incl. slice variants.

**Verdict for a 16B byte-classification loop today**: NOT usable on any released Go for arm64 as of 2026-07 (1.26 = amd64 only). Usable on **Go 1.27 RC1+** under GOEXPERIMENT=simd with unstable API — i.e. plausible for an experimental build tag, not for the production default until 1.27 GA (~Aug 2026) and probably not "stable" until the experiment graduates. The intrinsic path avoids the ABI0 call-overhead problem entirely (intrinsics inline into SSA).

## (2) Hand-written Go asm on NEON

**TBL nibble-classification pattern** (simdjson `arm64/simd.h`, verified source): `lookup_16` is literally one `vqtbl1q_u8`; full-byte classification = `shr<4>` for high nibble + `&0xF` low nibble + two TBL lookups + AND (Mula's algorithm; the canonical writeup is 0x80.pl "SIMD byte lookup" — site currently unreachable, technique confirmed via simdjson + Teddy README). Teddy (BurntSushi aho-corasick `packed/teddy/README.md`) is exactly this: 8 buckets, per-nibble bucket-union masks, `C = PSHUFB(A0,B0) & PSHUFB(A1,B1)`, LSB position → byte offset + bucket → verify.

**Pseudo-movemask on NEON** (Kutenin, ARM community blog "Porting x86 vector bitmask optimizations to Arm NEON", verified):
- `SHRN #4` on the u16-reinterpreted CMEQ result → 64-bit "nibble mask" (4 bits per byte) in ONE instruction; old glibc 4-instruction sequence (mov/dup/and/addp) → single shrn was a 10–15% strlen gain on SPEC 2017 distribution; ZSTD levels 5–9 +3.5–4.5%.
- Iterate hits: `RBIT`+`CLZ` (no ctz on aarch64), bit position /4; `&0x8888…` for one bit per byte; Kernighan `m &= m-1` to iterate.
- `UMAXP` for the pure "any hit?" loop test — on Neoverse N1 umaxp issues on V0/V1 while shrn is V1-only, so umaxp-existence-check + shrn-only-on-hit wins for sparse hits (glibc memchr pattern). **Directly applicable to your 1.43% anchor density: the fast path should be existence-test only.**
- Langdale (branchfree.org 2019 "ARM holes" post): 4×PMOVMSKB-equivalent for 64B via LD4 interleaved loads + 4×AND + 3×VBSL + 1 VPADDQ + extract, "strictly cheaper"; cut simdjson stage1 4.23→3.86 cycles/byte (~10%) on Ampere eMag. Note for Teddy-on-ARM: LD4 interleaving makes adjacent-byte predicate combination an AND except across 32-bit boundaries — he flags this as "a key consideration" for porting Teddy.
- Go's own `bytealg/indexbyte_arm64.s` uses the third variant: 32B/iter, VCMEQ + AND magic `0x40100401` + 2×VADDP → 64-bit syndrome (2 bits/byte), VORR+VADDP cheap early-exit inside the loop, RBIT+CLZ at exit. 32B-aligned via `BIC $0x1f`.

**Go assembler instruction coverage (checked go1.25.11 anames.go + doc.go locally)**: has `VTBL/VTBX`, `VCMEQ`, `VADDP`, `VAND`, `VUSHR`, `VSRI/VSLI`, `VLD1/VLD2/VLD4` (+.P post-increment), `VEXT`, `VRBIT`, `VADDV/VUADDLV`, `VBSL/VBIT`, `PRFM` (used in runtime asm_arm64.s: `PRFM (R0), PLDL1KEEP`). **`SHRN`/`VSHRN` is NOT in the mnemonic table, nor UMAXP/UMINP** — you'd need `WORD $0x…` raw encoding for Kutenin's shrn trick, or use the VADDP syndrome approach Go's stdlib itself uses. That's the single biggest assembler-surface gotcha.

**ABI cost (MEASURED, this host = Graviton3, CPU part 0xd40 = Neoverse V1)**: minimal ABI0 asm func (2 loads from FP + add + store) = **3.48 ns/call** vs noinline Go ABIInternal call = **1.93 ns/call**. So ABI0 stack-argument marshaling + wrapper ≈ **+1.5–3.5 ns per call**. At 64B per call that caps you at ~18 GB/s even with zero work; **per-call granularity must be ≥ the whole fragment (or ≥4KB blocks), never per-64B-block**. abi-internal.md confirms: user asm must target ABI0 ("ABIInternal is unstable"); ABI wrappers are auto-generated; #44065 (open, Backlog) tracks wrapper-bypass and is runtime-restricted. Practical mitigation used by stdlib: one asm entry point that loops internally over the whole buffer, NOSPLIT, no callbacks out.

**Maintainability / codegen tooling (avo doesn't do arm64 — confirmed; avo is x86-64 only)**. Real-world patterns:
- **Hand-written Plan9**: Go stdlib `bytealg` (indexbyte/count/equal/index `_arm64.s`) — the house style: alignment prologue, big aligned loop, syndrome extraction at exit.
- **goat (gorse-io/goat)**: C → clang -O3 → objdump → Go asm with raw `BYTE/WORD` directives + disasm comments; supports arm64; limitations: no calls, int64/float/pointer args only, "potentially BUGGY". Good for prototyping a NEON kernel written as C intrinsics.
- **asm2asm route (bytedance/sonic)**: Clang output mechanically converted; sonic arm64 works via this native-C path (README confirms ARM64 needs go1.20+; kernels compiled from C).
- **avo→arm64 lowering (klauspost/compress `zstd/seqdec_arm64.s`)**: "EXPERIMENTAL arm64 output lowered from an amd64 avo program", 2.7k lines, ABI0 FP-offset args, works in production zstd. Shows mechanical amd64→arm64 lowering is viable but ugly (labels still say `_amd64`).

## (3) SWAR headroom for the multiply chain

- **Fibonacci hashing** (probablydance, verified): index = `(hash * 11400714819323198485) >> (64-k)` — one multiply+shift, ~1.5ns incl. dependent shift; excellent scatter for similar/sequential keys (your trigram windows ARE maximally similar — adjacent windows share 2 bytes). Weakness: top input bit affects only one output bit → put the trigram bytes in the HIGH bits before multiply, or accept it since you only keep top bits anyway.
- **Shared-multiply idea, grounded**: 8 windows per 64-bit word currently = 8 multiplies. Known alternatives: (i) **pair pre-classification** — one 64KB (or hashed 8KB) table indexed by 2-byte pairs, looked up once per byte position, then a trigram is anchor-candidate only if pair(i,i+1) AND third-byte class agree; this replaces 8 mul+shift+load with 8 loads (parallel, L1-resident) + 8 ANDs — that's the **DFC direct-filter design** (NSDI'16, KAIST): 2-byte window into a small bitmap sized to L1/L2, progressive second filters, compact hash tables; paper's claim (paper PDF unreachable, repo confirmed: github.com/nfsp3k/DFC, CC BY-NC-SA — **license unusable commercially, reimplement from paper**) is ~2–3.6× over AC scalar (ESTIMATED, from memory of the paper — verify). (ii) **Per-byte 64-bit table lookup**: `class[b]` returns an 8-bit-per-lane classification byte; SWAR-combine `class[b0] & (class2[b1]) & (class3[b2])` shifted — one load per byte instead of one multiply per window; loads are 4-cycle L1 but you have 3 load pipes on V1 vs the single-multiply-pipe serialization you likely have now (MUL on Neoverse V1: results from memory ~2-3 cyc latency, limited pipes — ESTIMATED, could not fetch the V1 SOG, Arm doc pages render empty to fetchers).
- **Hyperscan's own SWAR path exists**: Langdale comment (2019 post comments) confirms multiply-based sign-bit gathering "dates back decades and is used in Hyperscan's SWAR path" — i.e., the mul-movemask approach you have is the known scalar fallback; the step up is the shuffle path, not a cleverer multiply.
- **FDR as SWAR alternative** (branchfree.org "Paper: Hyperscan" post, verified): "bucketed SIMD shift-or matcher with supercharacters", sweet spot "around 80 to tens of thousands of strings", works well at 128-bit (8 buckets×16); uses SIMD as a wide register, not for data parallelism. A **64-bit GPR shift-or FDR variant (8 buckets × 8 domain)** is implementable in pure Go with zero asm: per-byte table load + OR + shift — one load+or+shift per byte, no multiplies at all, and gives you bucketed identification like Teddy. This is the strongest "pure Go, no asm" candidate to beat 520 MB/s for (a).

## (4) Prefetch / dual-cursor

- `PRFM (Rn), PLDL1KEEP` is available in Go asm (runtime uses it). For pure Go, there is no prefetch intrinsic; the idiom is software-pipelined dual/quad-cursor: split the 1MB fragment into 2–4 interleaved streams processed in one loop so independent loads overlap. Lemire's MLP measurements (M1: "about 28 levels of memory parallelism"; his testingmlp tool) — Graviton3/V1 not measured in that post, but V1 supports ~dozens of outstanding misses (ESTIMATED); for L2-resident 1MB fragments, 2 cursors is typically enough to saturate the 3 load pipes; the win is hiding L2 latency (~13 cyc), not DRAM.
- Caveat from the same Lemire post: naive cost models fail — adding "free" adjacent reads made 2-wise 40% slower on M1; benchmark, don't assume.

## (5) Throughput ceilings on Graviton3 (this host, CPU part 0xd40 = Neoverse V1, 2.6 GHz)

**MEASURED here (Go 1.25.11, 1 MiB buffers, L2-resident)**:
- `bytes.IndexByte` miss-scan: **43.1 GB/s** (≈16.6 B/cycle — consistent with the 32B/iter VCMEQ loop bounded by 2×16B loads/cycle).
- `bytes.Equal`: **33.8 GB/s per stream** (67.6 GB/s total read).
- `bytes.ToLower` upper-ASCII 1MiB: **0.52 GB/s** — it allocates + runs a SCALAR byte loop (verified in `bytes/bytes.go`: `for i… if 'A'<=c<='Z'`); the all-ASCII-no-upper fast path just copies. So fused SWAR lowercasing in your scanner is already ~10× better than the stdlib path; never call bytes.ToLower in the hot pipeline.
- Chips&Cheese Graviton3 (verified article): 2.6 GHz, 2×256-bit SVE / inferred 4×128-bit NEON pipes but **measured NEON ≤3 IPC** (suspected register-file bandwidth limit), L1D 64KB 4-cycle, ~125×256-bit physical vector regs. No prose GB/s numbers (charts only).
- Ceiling framing: your 520 MB/s trigram stage = 0.2 B/cycle. IndexByte proves the machine does 16+ B/cycle on trivial classification; a Teddy-class NEON kernel doing ~10–15 ops per 16B chunk should land at **2–6 GB/s** (ESTIMATED: 16B / (4–8 cycles) at 2.6GHz), i.e. 4–10× your current stage throughput — but per your own e2e data the stage is only worth a few % of detector CPU now, so this matters only if it also subsumes verification work.

## (a) Beating 520 MB/s single-thread, pure Go — direct answers

1. **Teddy-style prefilter is the known technique** and it works on 128-bit NEON: BurntSushi's aho-corasick has a production **SlimNeon Teddy** (`packed/teddy/builder.rs`, cfg aarch64+neon, mask lengths 1–4, slim only — "we'd want at least 256-bit vectors" for Fat). Its bucket heuristics cap useful pattern counts (>16/32/48 patterns skip for mask len 1/2/3; len 4 uncapped) — 366 keywords is **above slim Teddy's sweet spot**; Hyperscan's split is Teddy for small groups, **FDR for ~80+ to tens of thousands** → for 366 patterns the literature answer is **FDR (bucketed shift-or)**, not Teddy. Vectorscan (VectorCamp fork, "100% functional" on NEON/ASIMD, teddy.c+fdr.c with arm/ subdir) proves both run on NEON in production.
2. In **pure Go without asm**: 64-bit-register FDR (8 buckets, shift-or, per-byte table load) or DFC-style 2-byte direct filter + your existing rarest-trigram confirm; both replace the multiply chain with table loads and are the plausible 1.5–3× scalar wins. Note DFC reference code license is CC BY-NC-SA (non-commercial) — reimplement, don't port.
3. **Rarest-byte packed-pair (memchr memmem model, verified source)**: pick 2 rare bytes by background frequency, SIMD compare both offsets, verify; plus **adaptive prefilter disabling** (after 50 uses, if avg skip <8 bytes → mark inert). Your root-skip self-disable is the same idea; consider the same adaptive stats for trigram vs AC choice per-corpus.

## (b) What Teddy/FDR-class SIMD buys on NEON with Go's assembler

- Kernel shape per 16B: 1×VLD1 + VUSHR/VAND (nibbles) + 2×VTBL + 1×VAND (+2 more TBL+AND per extra mask byte) + VEXT for cross-chunk alignment + any-hit test (VADDP-syndrome since **SHRN is missing from Go's assembler**; use `WORD` encodings if you want shrn/umaxp). All required mnemonics except SHRN/UMAXP exist (verified anames.go).
- Expected: anchor detection at multiple GB/s vs 0.52 GB/s now (ESTIMATED above), with **bucket ID for free** → collapses "which keyword" dedupe work. Slim-Teddy's 8-bucket / 128-bit limit means 366 patterns → ~46 patterns/bucket → high verify load; mitigations: 3–4 byte fingerprints (Teddy mask len 3/4, supported in the Rust NEON impl), or restrict Teddy to the ~top-N-frequency keywords and keep the trigram/AC path for the rest.
- ABI: one call per fragment (1MB) makes the 3.5ns ABI0 overhead irrelevant; per-4KB-block calls cost ~0.1% — fine. GOEXPERIMENT=simd on Go 1.27 gives the same kernel WITHOUT asm (PermuteOrZero/Equal/And/IsZero inline as intrinsics) — likely the maintainable endgame; asm is the today-option.

## (c) Hit-window verification stage (291 rules)

- **Replace per-rule `bytes.Index` discovery with bucketed identification from the prefilter itself**: Teddy/FDR-class scanners return (position, bucket) so occurrence discovery is a byproduct — the literature-standard fix; Hyperscan's FDR "confirm" step is a per-bucket compact hash confirm (fdr_confirm.h in vectorscan), not per-pattern re-search.
- **daachorse-style double-array AC** (verified README): 12 bytes/state compact double-array, constant-time transitions, linear scan — a cache-optimal static structure if you keep an automaton for verification; Rust-only, but the double-array layout is trivially portable to Go and is the succinct-structure answer to "AC but smaller than 944KB failTrans16" (366 keywords ≈ few thousand states ≈ ~30–50KB, L1/L2-resident).
- **memchr memmem tricks that transfer** (verified): packed-pair with frequency-ranked byte choice for the per-rule Index; 32-byte needle cap on memcmp-confirm to bound false-positive cost; Rabin-Karp fallback for tiny windows; adaptive inerting.
- Succinct rank/select over merged intervals: plausible for interval-merge bookkeeping (bitmap + popcount via `math/bits.OnesCount64` is 1 ins/word on arm64) but the interval count per window is small — the win is in eliminating the discovery scans, not compressing them. No published system does "succinct verification" beyond compact-hash confirm; that's the state of the art.
